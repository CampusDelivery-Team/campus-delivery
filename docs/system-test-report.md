## 2. 测试目的

本次测试不是以简单增删改查数量为目标，而是验证校园综合跑腿与代取服务管理系统的完整业务链路、权限边界、事务一致性、状态机、重复提交和异常输入处理。重点证明以下能力：

1. 核心业务规则位于 Service 层，Controller 不直接访问数据库。
2. 抢单、支付等高风险写操作具有事务边界和行锁设计。
3. 任务、支付、退款等对象不能随意进行非法状态转换。
4. 越权、空字段、非法枚举、不存在 ID、重复提交等异常不会造成脏数据。
5. 测试结果区分“已自动执行”“静态检查通过”“待数据库执行”和“已知缺陷”，不把未执行用例写成通过。

## 4. 当前测试能力与缺失分析

### 4.1 已具备能力

- 小型 `CampusDelivery.Tests` 测试工程覆盖 `AssignService`、`TaskService`、`PaymentService`、`ReviewService`、`AddressService`、`SettlementService` 和 `ReportService` 七个高价值业务服务。
- 使用仓储接口测试替身隔离 Oracle，能够稳定验证 Service 的规则、事务提交/回滚和模拟行锁下的并发结果。
- 自动检查 24 张表、全部 MVC POST 防伪令牌、五层边界、仓储层 `FOR UPDATE` 以及连接字符串外置。
- 代码中抢单先锁定任务行和跑腿员行，再在同一事务内更新任务、跑腿员、接派记录和状态日志。
- 已形成数据库端到端手工步骤、并发复核 SQL 和证据留存规范，见 `manual-system-test-guide.md`。

### 4.2 当前缺失

- 仓库已有自动化测试工程和本地质量脚本，但尚未配置持续集成工作流。
- MVC 接口使用 Cookie 和 Anti-forgery Token，不适合直接提交一个带固定令牌的 Postman 集合；已提供可复现的 Postman/浏览器执行说明。
- 本轮数据库验收使用专用共享库记录并保留审计证据；若要周期性自动执行，仍需建设可重建的独立测试库和持续集成工作流。
- 本轮没有进行浏览器厂商兼容性矩阵和压力/容量测试；这些不影响本次业务规则验收结论。

## 6. 测试方法

### 6.1 自动化业务测试

通过仓储接口测试替身直接调用 Service，验证输入规范化、状态机、事务提交/回滚、幂等和并发结果。测试不依赖数据库账号，不写入真实业务数据。

并发测试替身使用同一个异步信号量模拟任务行锁：两个跑腿员同时请求同一 `WAITING` 任务，两个请求都进入业务服务，但只有先获得锁的请求能提交；第二个请求获得锁后重新读取状态并回滚。

### 6.2 静态质量门禁

`scripts/run-tests.ps1` 在测试后检查：

- 建表数量不少于 12；当前为 24。
- 所有 `[HttpPost]` Action 均有 `[ValidateAntiForgeryToken]`；当前为 47/47。
- Controller 不引用 Repository 接口。
- Service 中不存在 Oracle Command/Connection 或 `CommandText`。
- Repository 中存在真实的 `FOR UPDATE` 行锁；当前检出 14 处。
- `ConnectionStrings:OracleDb` 在配置文件中声明。

### 6.3 数据库手工/集成测试

在已授权的共享 Oracle 中使用专用标识账号和数据按真实页面完成主流程，用两个独立 Cookie/Anti-forgery 会话执行并发抢单、地址新增和结算更新。每一步同时检查 HTTP/页面结果和数据库记录，完整证据见 `test-evidence/manual/2026-08-22-shared-e2e.md`。

### 6.4 状态机和异常测试

采用合法路径、跳步路径、重复提交、非法枚举、空字段、跨用户访问和不存在 ID 组合验证。数据库用例执行前后记录任务、接派、支付、退款和日志表状态。
