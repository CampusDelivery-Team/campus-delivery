## 2. 设计结果

项目要求的两类职责落实为三个 Oracle 触发器：

| 类型 | 触发器 | 结果 |
| --- | --- | --- |
| 任务状态审计 | `TRG_TASK_STATUS_AUDIT` | 合法路径记 `PASS`，未知路径记 `ABNORMAL` |
| 关键数据变更审计 | `TRG_PAYMENT_CHANGE_AUDIT` | 审计支付创建、状态及金额等关键列变化 |
| 关键数据变更审计 | `TRG_REFUND_CHANGE_AUDIT` | 审计退款申请、审核及关键列变化 |

没有直接监听 `tasks.task_status` 后再次插入 `task_status_logs`。原因是应用和
`SP_ACCEPT_TASK_ATOMIC` 已经负责写真实状态日志；重复写会产生两条日志，并且
Oracle 数据库会无法可靠获得网站当前登录人的 `operator_user_id`。

## 3. 测试结果

| 测试内容 | 实际结果 | 结论 |
| --- | --- | --- |
| 编译和对象状态 | 三个触发器均 `ENABLED`，编译错误 0 | 通过 |
| 合法任务流转 | `WAITING -> ASSIGNED` 生成 `LOG/PASS` | 通过 |
| 非法任务流转 | `WAITING -> FINISHED` 生成 `LOG/ABNORMAL` | 通过 |
| 事务一致性 | 保存点后新增业务行和审计行，回滚后两者同时消失 | 通过 |
| 支付合法变化 | 创建 `UNPAID`、再变为 `PAID`，均为 `PASS` | 通过 |
| 支付关键数据异常 | `PAID` 后改金额记为 `ABNORMAL` | 通过 |
| 支付状态倒退 | `PAID -> UNPAID` 记为 `ABNORMAL` | 通过 |
| 空更新去噪 | `SET pay_status=pay_status` 没有新增审计 | 通过 |
| 退款合法变化 | `APPLY -> APPROVED` 记为 `PASS` | 通过 |
| 退款状态倒退 | `APPROVED -> APPLY` 记为 `ABNORMAL` | 通过 |
| 已通过退款再改关键内容 | 记为 `ABNORMAL`，测试后回滚 | 通过 |
| 回滚脚本 | 删除触发器后 9 条历史审计仍保留 | 通过 |
| 再次创建 | 三个触发器恢复为 `ENABLED`，错误仍为 0 | 通过 |

最终保留 9 条隔离审计记录。`AUDIT_ID` 从 2 跳到 4，是事务回滚测试消耗了
identity 编号但回滚了业务与审计行，属于 Oracle 正常行为。

## 4. 环境边界

- 个人 Schema 原本没有表空间配额。测试时临时设置 10 MB，完成后已恢复为 0。
- 没有给个人账号新增 `CREATE TABLE` 权限。
- 原有指向 `APPUSER` 的同义词没有删除或替换。
- `APPUSER` 当前触发器数量仍为 0，正式库没有因为本次测试发生变化。
- 个人 Schema 保留 `M2_` 隔离对象，方便使用 DBeaver 执行只读复核 SQL 和截图。

## 5. 总体结论

触发器脚本的创建、合法路径、异常路径、空更新、事务回滚、对象回滚和重新创建
均已通过个人 Schema 隔离测试。当前可以提交代码和测试记录，但在数据库负责人
确认自动新增审计记录的业务影响之前，不应把脚本部署到 `APPUSER`。
