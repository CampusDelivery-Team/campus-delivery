# 组员9：结算、审计与报表测试说明

本文档用于说明组员9负责模块的测试思路。重点不是简单记录“点了哪些按钮”，而是从数据库设计、后端实现和业务规则出发，解释每个测试用例验证的逻辑、为什么需要验证，以及测试现象如何证明系统行为正确。

## 1. 测试范围

组员9负责模块为“结算、审计与报表”，对应测试计划中的 TC-SETTLE-01 至 TC-SETTLE-10。

主要功能包括：

- 管理员生成跑腿员结算单。
- 防止同一支付记录重复结算。
- 排除存在退款或投诉争议的支付记录。
- 管理结算单状态流转。
- 对支付、退款、状态日志进行审计。
- 查看统计面板。
- 生成、查看、导出业务报表。
- 跑腿员查看本人结算记录。

## 2. 前置知识

本模块涉及的知识点较多，但测试时最需要掌握的是以下几项。

### 2.1 Oracle Schema 与业务表

Oracle 中一个用户通常对应一个 Schema。项目业务表位于本项目账号对应的 Schema 下，例如 `APPUSER`。测试 SQL 中建议显式写出 Schema 前缀，避免误查其他用户的同名表。

本模块常用表如下：

| 表名 | 作用 |
| --- | --- |
| `payments` | 支付记录，表示用户是否已支付以及支付金额 |
| `tasks` | 任务记录，表示订单状态、发布者、任务类型等 |
| `assign_records` | 接单/派单记录，连接任务与跑腿员 |
| `refunds` | 退款记录，用于判断支付是否存在售后争议 |
| `complaints` | 投诉记录，用于判断订单是否存在处理中的争议 |
| `settlements` | 结算单主表，保存跑腿员结算汇总金额和状态 |
| `settlement_payment_items` | 结算明细表，记录一个结算单包含哪些支付记录 |
| `audit_logs` | 审计主表，记录审计对象、结果、时间、备注 |
| `audit_payment_checks` | 支付审计关联表 |
| `audit_refund_checks` | 退款审计关联表 |
| `audit_status_log_checks` | 状态日志审计关联表 |
| `reports` | 报表主表 |
| `report_audit_items` | 报表与审计记录关联表 |

其中 `settlements` 与 `settlement_payment_items` 是一对多关系：一张结算单可以包含多笔支付记录。

### 2.2 后端分层结构

本项目后端采用常见的分层写法：

```text
Controller -> Service -> Repository -> Oracle Database
```

各层职责大致如下：

| 层次 | 作用 |
| --- | --- |
| Controller | 接收页面请求，处理登录角色，返回页面或重定向 |
| Service | 实现业务规则，例如结算条件、状态机、报表生成逻辑 |
| Repository | 执行 SQL，读取或写入 Oracle 数据库 |
| Database | 持久化保存业务数据 |

因此测试页面现象时，不能只看按钮是否能点，还要用 SQL 验证数据库是否产生了正确变化。

### 2.3 结算候选支付的判断条件

一笔支付记录可以进入结算候选，通常需要同时满足：

- 支付状态为已支付，例如 `PAID`。
- 关联任务已经完成，例如 `FINISHED`。
- 支付记录归属于当前要结算的跑腿员。
- 该支付记录尚未出现在 `settlement_payment_items` 中。
- 该支付记录不存在活动退款。
- 该支付记录关联任务不存在处理中投诉。

这个规则的目的，是保证结算只针对已经完成、已经付款、没有争议、没有重复结算的收入。

### 2.4 结算单与结算明细

结算单主表 `settlements` 保存汇总信息：

- `runner_id`：跑腿员编号。
- `order_total`：订单总金额。
- `platform_fee`：平台抽成。
- `net_income`：跑腿员实际收入。
- `settlement_status`：结算状态。

结算明细表 `settlement_payment_items` 保存每张结算单包含哪些支付：

- `settlement_id`：结算单编号。
- `payment_id`：支付记录编号。

这种设计把“汇总金额”和“明细来源”分开，可以支持后续追溯：如果结算金额有问题，可以回查到底是哪几笔支付组成了这张结算单。

### 2.5 状态机思想

结算状态不是任意切换的，而是通过状态机限制合法流转。当前模块的核心规则是：

```text
WAITING -> DONE
WAITING -> BLOCKED
BLOCKED -> WAITING
DONE 为终态，不允许继续修改
```

这样设计是为了保护财务状态。尤其是 `DONE` 表示结算已完成，如果允许再随意改回，会造成财务记录不可信。

### 2.6 审计日志设计

审计功能采用“主表 + 关联表”的设计。

`audit_logs` 统一记录审计结果，例如：

- 审计对象类型。
- 审计结果。
- 审计时间。
- 异常说明。

具体审计了哪一条支付、退款或状态日志，则分别写入：

- `audit_payment_checks`
- `audit_refund_checks`
- `audit_status_log_checks`

这种设计的好处是：审计主表保持统一，具体对象又能被准确追溯。测试时需要同时检查主表和对应关联表，才能证明审计记录写完整了。

### 2.7 报表统计口径

报表不是简单导出某张表，而是按报表类型和月份统计业务数据。当前模块支持的报表类型包括：

- 订单报表。
- 支付报表。
- 投诉报表。

报表按 `yyyy-MM` 形式的统计周期归集数据。由于部分业务表没有独立的支付时间或投诉提交时间字段，实现中会使用关联任务的时间字段作为统计口径。这一点在测试和答辩时需要说明清楚：报表统计的是系统当前可获得时间字段下的业务归集结果。

### 2.8 管理员端与跑腿员端权限

管理员负责管理性操作：

- 生成结算单。
- 修改结算状态。
- 创建审计。
- 生成和导出报表。

跑腿员只负责查看自己的结算：

- 查看本人结算列表。
- 查看本人结算详情。
- 不能查看其他跑腿员结算。
- 不能修改结算状态。

因此测试时需要分别使用管理员账号和跑腿员账号，验证角色边界。

## 3. 测试环境建议

建议使用本地后端连接云端 Oracle 数据库进行测试：

```text
本地浏览器 -> 本地 dotnet 后端 -> SSH 隧道 localhost:15210 -> 云端 Oracle
```

这样可以保证测试的是当前仓库 `test` 分支代码，而不是不确定版本的线上部署页面。

启动顺序建议：

1. 切换并更新 `test` 分支。
2. 打开 SSH 隧道，并保持窗口不关闭。
3. 设置 `ConnectionStrings__OracleDb` 环境变量。
4. 启动后端。
5. 浏览器访问本地后端地址。
6. 使用 DBeaver 或 DataGrip 连接 `localhost:15210/orclpdb1` 查询数据库证据。

## 4. 测试用例说明

### 4.1 TC-SETTLE-01：生成结算单

#### 测试目标

验证管理员可以根据跑腿员的可结算支付记录生成结算单，并正确写入结算主表和明细表。

#### 为什么要测

结算是本模块的核心业务。如果生成结算单时金额错误、明细缺失或状态不正确，会直接影响跑腿员收入和平台财务数据。

#### 涉及设计

涉及页面：

- `/Settlement`
- `/Settlement/Candidates`
- `/Settlement/Details/{settlement_id}`

涉及数据表：

- `payments`
- `tasks`
- `assign_records`
- `settlements`
- `settlement_payment_items`

#### 操作步骤

1. 使用管理员账号登录。
2. 进入结算候选页面。
3. 选择一个存在可结算支付记录的跑腿员。
4. 点击生成结算单。
5. 进入结算详情页查看结算金额和明细。
6. 使用 SQL 查询新生成的结算单和明细。

#### 预期现象

页面上应生成一条新的结算单，状态为 `WAITING`。结算金额包括订单总额、平台抽成和跑腿员净收入。数据库中 `settlements` 新增主记录，`settlement_payment_items` 新增对应明细记录。

#### 原理解释

后端生成结算单时，会先从数据库查询当前跑腿员满足条件的支付记录，然后计算汇总金额。汇总结果写入 `settlements`，每一笔支付写入 `settlement_payment_items`。这两个写入结果共同证明结算单生成完整。

#### 参考 SQL

```sql
SELECT settlement_id, runner_id, order_total, platform_fee, net_income, settlement_status
FROM APPUSER.settlements
ORDER BY settlement_id DESC;
```

```sql
SELECT settlement_id, payment_id
FROM APPUSER.settlement_payment_items
WHERE settlement_id = :sid
ORDER BY payment_id;
```

#### 测试现象展示与解释

需要展示：

- 结算候选页面截图。
- 生成后的结算详情页截图。
- `settlements` 查询结果截图。
- `settlement_payment_items` 查询结果截图。

如果页面金额与 SQL 中 `order_total`、`platform_fee`、`net_income` 一致，且明细表中 payment 数量与详情页展示一致，则说明结算生成逻辑正确。

### 4.2 TC-SETTLE-02：重复结算限制

#### 测试目标

验证同一笔支付记录不能被重复纳入多个结算单。

#### 为什么要测

重复结算是财务系统中的严重问题。如果同一个 `payment_id` 出现在多张结算单中，跑腿员可能被重复发放收入，平台账务也会失真。

#### 涉及设计

涉及页面：

- `/Settlement`
- `/Settlement/Candidates`

涉及数据表：

- `settlement_payment_items`

#### 操作步骤

1. 先完成 TC-SETTLE-01，生成一张包含若干支付记录的结算单。
2. 再次进入结算候选页面。
3. 查看已结算过的支付记录是否从候选列表中消失。
4. 如再次生成结算单，检查新结算单是否不包含已结算 payment。
5. 使用 SQL 检查是否存在重复 `payment_id`。

#### 预期现象

已结算过的支付记录不再出现在候选池中。同一 `payment_id` 在 `settlement_payment_items` 中最多出现一次。

#### 原理解释

候选查询会排除已经存在于 `settlement_payment_items` 的支付记录。该表不仅是结算明细，也是判断“是否已经结算过”的依据。

#### 参考 SQL

```sql
SELECT payment_id, COUNT(*) AS cnt
FROM APPUSER.settlement_payment_items
GROUP BY payment_id
HAVING COUNT(*) > 1;
```

#### 测试现象展示与解释

需要展示：

- 再次进入候选列表时，原 payment 不再出现的截图。
- 重复检查 SQL 的查询结果截图。

如果重复检查 SQL 返回空结果，说明没有支付记录被重复结算。

### 4.3 TC-SETTLE-03：跑腿员归属校验

#### 测试目标

验证系统不会把跑腿员 A 的支付记录结算给跑腿员 B，也不会允许跑腿员查看不属于自己的结算详情。

#### 为什么要测

结算归属错误会导致收入发错人。对于跑腿员端页面，如果能查看别人的结算，也属于权限泄漏。

#### 涉及设计

涉及页面：

- `/Settlement/Candidates`
- `/Settlement/My`
- `/Settlement/MyDetails/{settlement_id}`

涉及数据表：

- `assign_records`
- `settlements`

#### 操作步骤

管理员侧：

1. 找到一笔明确属于跑腿员 A 的支付记录。
2. 尝试观察候选页面中该支付是否只归入 A 的候选列表。

跑腿员侧：

1. 使用跑腿员账号登录。
2. 进入 `/Settlement/My`。
3. 确认列表只展示当前跑腿员结算单。
4. 尝试访问其他跑腿员结算详情地址。

#### 预期现象

管理员生成结算时，支付记录只会归属实际完成任务的跑腿员。跑腿员端只能看到本人结算，访问其他跑腿员结算详情应被拒绝或不显示。

#### 原理解释

支付记录本身不直接代表跑腿员收入，需要通过任务接单记录确定对应跑腿员。后端在查询候选或跑腿员本人结算时，会带上当前跑腿员身份条件，避免跨跑腿员访问。

#### 参考 SQL

```sql
SELECT s.settlement_id, s.runner_id, s.order_total, s.settlement_status
FROM APPUSER.settlements s
WHERE s.runner_id = :runner_id
ORDER BY s.settlement_id DESC;
```

#### 测试现象展示与解释

需要展示：

- 跑腿员本人结算列表截图。
- 尝试访问其他结算详情失败的截图。
- 对应 runner_id 的结算 SQL 截图。

如果页面只展示当前跑腿员对应的 `runner_id` 数据，则说明权限隔离生效。

### 4.4 TC-SETTLE-04：退款/投诉中支付不结算

#### 测试目标

验证存在退款或投诉争议的支付记录不会进入结算明细。

#### 为什么要测

退款和投诉都表示订单收入可能存在争议。如果此类支付先进入结算，后续退款或投诉处理可能导致平台已经把钱结给跑腿员，但用户侧仍需要退款或赔付。

#### 涉及设计

涉及页面：

- `/Settlement/Candidates`
- `/Settlement/Details/{settlement_id}`

涉及数据表：

- `refunds`
- `complaints`
- `settlement_payment_items`

#### 操作步骤

1. 查询当前数据库中是否存在活动退款记录。
2. 查询当前数据库中是否存在处理中投诉记录。
3. 找到关联 payment 或 task。
4. 在结算候选页面确认相关支付不出现。
5. 如生成结算单，确认明细中不包含这些支付。

#### 预期现象

存在活动退款或处理中投诉的支付记录不会出现在候选列表，也不会写入 `settlement_payment_items`。

#### 原理解释

候选查询不仅检查支付和任务状态，还会排除争议数据。退款和投诉属于财务风险条件，系统需要等待处理结束后再判断是否可以结算。

#### 参考 SQL

```sql
SELECT refund_id, payment_id, process_status
FROM APPUSER.refunds
WHERE process_status IN ('APPLY', 'APPROVED', 'DONE');
```

```sql
SELECT complaint_id, record_id, process_status
FROM APPUSER.complaints
WHERE process_status IN ('SUBMITTED', 'PROCESSING');
```

```sql
SELECT settlement_id, payment_id
FROM APPUSER.settlement_payment_items
WHERE payment_id = :payment_id;
```

#### 测试现象展示与解释

需要展示：

- 退款或投诉数据 SQL 截图。
- 候选列表中不包含该支付的页面截图。
- 明细表中查不到该 payment 的 SQL 截图。

如果当前数据库没有退款或投诉测试数据，则该用例应记录为“阻塞：缺少测试数据”，不能直接写通过。

### 4.5 TC-SETTLE-05：结算状态机

#### 测试目标

验证结算状态只能按业务允许的路径变化。

#### 为什么要测

结算状态体现财务处理进度。如果允许任意修改，已完成结算可能被错误回滚或重复处理，影响数据可信度。

#### 涉及设计

涉及页面：

- `/Settlement/Details/{settlement_id}`

涉及数据表：

- `settlements`

#### 操作步骤

1. 准备一条状态为 `WAITING` 的结算单。
2. 将其改为 `BLOCKED`。
3. 将 `BLOCKED` 恢复为 `WAITING`。
4. 将 `WAITING` 改为 `DONE`。
5. 尝试再次修改 `DONE` 状态。
6. 使用 SQL 查看最终状态。

#### 预期现象

系统只允许以下流转：

```text
WAITING -> DONE
WAITING -> BLOCKED
BLOCKED -> WAITING
```

当结算单变为 `DONE` 后，继续修改应失败。

#### 原理解释

后端 Service 层会检查当前状态和目标状态，只有合法状态转换才允许更新数据库。`DONE` 被视为终态，因此不允许继续变化。

#### 参考 SQL

```sql
SELECT settlement_id, runner_id, settlement_status
FROM APPUSER.settlements
WHERE settlement_id = :sid;
```

#### 测试现象展示与解释

需要展示：

- 合法状态变化成功的页面截图。
- 非法状态变化失败的提示截图。
- 数据库最终状态截图。

如果数据库状态与页面状态一致，且非法状态没有被写入，则说明状态机控制有效。

### 4.6 TC-SETTLE-06：三类审计

#### 测试目标

验证管理员可以分别对支付、退款、状态日志进行审计，并且审计主表和关联表同时正确写入。

#### 为什么要测

审计功能的价值在于可追溯。如果只写了审计结果，但没有记录审计对象，就无法知道这条审计针对哪笔支付、退款或状态日志。

#### 涉及设计

涉及页面：

- `/Audit`
- `/Audit/Create`

涉及数据表：

- `audit_logs`
- `audit_payment_checks`
- `audit_refund_checks`
- `audit_status_log_checks`

#### 操作步骤

1. 使用管理员账号进入审计创建页面。
2. 选择支付审计，填写结果和备注并提交。
3. 选择退款审计，填写结果和备注并提交。
4. 选择状态日志审计，填写结果和备注并提交。
5. 查询审计主表和三类关联表。

#### 预期现象

每次审计都会在 `audit_logs` 中新增一条记录，同时在对应关联表中新增一条对象关联记录。

#### 原理解释

审计创建需要保证主记录和关联记录一起写入。如果只写入其中一个，数据就不完整。因此该功能通常需要在同一事务中完成。

#### 参考 SQL

```sql
SELECT audit_id, audit_object, audit_result, audited_at, exception_note
FROM APPUSER.audit_logs
ORDER BY audit_id DESC
FETCH FIRST 20 ROWS ONLY;
```

```sql
SELECT audit_id, payment_id
FROM APPUSER.audit_payment_checks
ORDER BY audit_id DESC;
```

```sql
SELECT audit_id, refund_id
FROM APPUSER.audit_refund_checks
ORDER BY audit_id DESC;
```

```sql
SELECT audit_id, log_id
FROM APPUSER.audit_status_log_checks
ORDER BY audit_id DESC;
```

#### 测试现象展示与解释

需要展示：

- 三类审计提交页面或结果页面截图。
- `audit_logs` 最新记录截图。
- 三张关联表中对应记录截图。

如果每条审计都能在主表和对应关联表中找到，说明审计记录具备完整追溯能力。

### 4.7 TC-SETTLE-07：统计面板

#### 测试目标

验证统计面板展示的数据与数据库汇总结果一致。

#### 为什么要测

### 4.8 TC-SETTLE-08：报表生成与导出

#### 测试目标

### 4.10 TC-SETTLE-10：跑腿员查看本人结算

#### 测试目标

验证跑腿员可以查看自己的结算记录和详情，但不能查看他人的结算，也不能进行管理员操作。

#### 为什么要测

跑腿员端结算查看是财务透明性的体现，但权限必须被限制在本人范围内。如果跑腿员可以查看他人结算，属于隐私和权限问题。

#### 涉及设计

涉及页面：

- `/Settlement/My`
- `/Settlement/MyDetails/{settlement_id}`

- `settlement_payment_items`

2. 进入 `/Settlement/My`。
3. 查看本人结算列表。

5. 尝试访问其他跑腿员结算详情。
6. 检查页面是否没有管理员操作按钮。
