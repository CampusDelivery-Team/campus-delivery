# 设计调整说明

> 版本：1.2　日期：2026-09-10

> 本文“已落地”指当前仓库代码和迁移脚本已经实现；`008`、`009` 是否已部署到共享 Oracle，以 `database/oracle/README.md` 的共享库状态和实际查询结果为准。

## 1. 调整背景

数据库设计文档在系统编码前完成。实现阶段根据真实业务闭环、并发安全和可验收性进行了细化，但没有改变 24 张关系表的主体结构，也没有破坏第三范式、主外键及多对多联系设计。当前实现仍采用表现层、控制器层、服务层、仓储接口层和数据访问层组成的 MVC 五层结构。

## 2. 已落地的主要调整

| 调整项 | 当前实现 | 调整理由 |
| --- | --- | --- |
| 任务与支付流程 | 发布后直接进入 `WAITING`；配送至 `WAIT_CONFIRM` 后由发布者确认并付款，支付成功才进入 `FINISHED` | 系统定位为履约型跑腿服务，避免任务未完成即产生正式收款 |
| 状态机与事务 | 抢单、派单、配送、支付、退款、结算均限制合法状态迁移，跨表写入使用事务，竞争场景使用行锁 | 防止重复接单、重复支付、状态回退及并发脏数据 |
| 数据库过程接入 | 账号封禁/解封、默认地址切换、跑腿员审核和原子接单均由 Repository 调用 Oracle 过程；过程返回稳定结果码，提交与回滚由后端控制 | 消除跨表业务写入的重复 SQL，并让数据库过程可真正服务于应用事务 |
| 账户与权限 | 密码使用带盐哈希；47/47 个 POST Action 校验防伪令牌；Cookie 请求期间重新核验账号状态和角色 | 防止明文密码、跨站请求伪造及封禁后旧会话继续使用 |
| 数据完整性 | 增加大小写/空格归一化唯一索引、单默认地址约束、评价唯一约束，并保留服务类型与节点的联合规则 | 将关键业务唯一性同时落实到 Service 和数据库层 |
| 价格与信誉边界 | 发布者填写非负附加费，后端调用数据库计价函数按最新基础费生成任务总价；信誉分在应用和数据库层均限制为0至100 | 保留用户合理加价，防止客户端伪造低价，并避免信誉分越界 |
| 报表与审计 | 报表按真实业务 SQL 生成指标和明细，关联审计依据，支持 CSV 导出及状态更新 | 避免只有报表元数据而没有可核验业务结果 |
| 测试与配置 | 连接字符串外置；当前62项自动化测试通过，静态门禁和 Oracle 验证脚本均已准备 | 便于部署修改、回归验证和答辩说明；共享库结果仍须由管理员实际执行后确认 |

## 3. 答辩前建议的小范围修正

1. 为当前接单跑腿员提供经过权限校验的任务专属明细查看入口，快递取件码等敏感字段只对发布者、当前跑腿员和管理员可见。
2. 发布前核对基础数据脚本预期的 4 条服务节点绑定。2026-08-22 检查发现共享库缺少“外卖分发—外卖分发点”绑定，该问题属于部署数据漂移，需通过管理页面或初始化脚本恢复，不应通过放宽后端校验绕过。

## 4. 本轮不建议扩展的内容

自动距离计价、节点到站登记、外部取件码核验、完成凭证上传、超时自动签收和接单后取消罚则需要地图、文件存储、定时任务或第三方核验能力，也会新增状态和异常分支。它们保留为后续扩展方向，本轮不为追求表面完整而临时加入，以免破坏已经通过验收的主业务闭环。

## 5. 结论

本次调整属于实现细化和安全加固，不是推翻数据库设计。答辩时应以当前已运行代码和测试证据为准，说明“设计文档给出完整业务蓝图，实际版本优先保证可运行、可验证的核心闭环”，并如实区分已实现功能、建议修正项和后续扩展项。
